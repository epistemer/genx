## Context

ADR 0001 picks jq as the one query language, run in-process. The library is
`github.com/itchyny/gojq`. The prototype ran on the C jq. Queries come from
other modules, so they must be deterministic and unable to read anything but
their input.

## What was tried

gojq v0.12.20 against jq 1.7.

| Check | Result |
|-------|--------|
| i18n's labels query (i18n ADR 0003), three inputs | Same values as jq. jq keeps an object's keys in insertion order; gojq sorts them. Compared with `jq -S`, byte-identical. Both error cases give the same message |
| A query's `error(...)` | Reaches Go as `gojq.ValueError`; `Value()` is the message without a prefix |
| `pascal` over 70 names | Identical on both, once written with `[^\p{L}\p{N}]+`: Go's `[[:alnum:]]` is ASCII-only, Oniguruma's isn't |
| `group_by` | Stable: input order kept inside each group, 10,000 elements with many ties |
| Key order of `to_entries`, `.[]`, `with_entries`, `tostream`, `tojson`, 100 runs | Identical every run; keys sorted. gojq has no `keys_unsorted` |
| Integers above 2^53 | Lost with plain `json.Unmarshal`; kept with `Decoder.UseNumber()`, also through arithmetic. A Go `int64` input panics: inputs must be `int`, `*big.Int`, `json.Number` or `float64` |
| `$ENV`, `env` | `{}` without an environment loader |
| `input`, `inputs` | Errors without an input iterator |
| `now` and the date functions | Read the clock or the time zone |
| `RunWithContext`, 200 ms deadline | Stops `def f: f; f`, `[range(1e9)]` and `repeat(1)` within 4 ms; `[range(1e9)]` peaks at about 21 MB |
| `test("(a+)+$")` on a long string | 4 ms: Go's regexp is linear |
| 2.6 MB of labels (15,000 labels, 400 files) | Decode 54 ms, compile 0.3 ms, run 144 ms; peak RSS 44 MB |

## Decision

genx embeds gojq, pinned, as the query engine.

- Domain files are decoded with `UseNumber()`; YAML inputs are converted to
  the same types.
- gojq gets no environment loader, no module loader and no input iterator.
- Before compiling, genx walks the parsed query and refuses these, with a
  message naming the function and the generator:
  - the clock and time zone: `now`, `mktime`, `gmtime`, `localtime`,
    `strftime`, `strflocaltime`, `strptime`, `todate`, `fromdate`, `date`,
    `todateiso8601`, `fromdateiso8601`, `dateadd`, `datesub`;
  - the environment: `env`, `$ENV`;
  - other input: `input`, `inputs`, `input_filename`, `input_line_number`;
  - side channels: `debug`, `stderr`, `halt`, `halt_error`;
  - modules: `import`, `include`, `get_search_list`, `modulemeta`,
    `$__loc__`.
- Every query runs under a context with a timeout (M2.3 picks the value;
  the spike suggests seconds, not minutes).
- The interface says "jq as gojq implements it", with the version, and that
  object keys come out sorted.

The kill criterion isn't met: deterministic, stoppable, no precision loss,
and 2 MB in about 0.2 s and 44 MB.

## Consequences

- New dependencies: gojq (MIT) and its one dependency, `timefmt-go` (MIT).
  The refused list makes the latter unreachable from a query.
- A generator author can't rely on key order inside an object. Arrays keep
  their order, which is what `labels/v1` needs.
- `[[:alnum:]]` and similar POSIX classes differ from the C jq. The guide
  for generator authors (M7.4) says to use `\p{L}` and `\p{N}`.
- No custom functions are added (definition of done, 6).
